# Future enterprise customer OAuth reference

Author: **Kehinde Bade**

This is an optional future enterprise plan, not the selected public demo. The user chose server-issued synthetic A/B identity sessions without Salesforce; see GEMINI_DEMO.md. No callback adaptation is being implemented now. The optional enterprise target would be Render: customer authentication, an agent request proposed by Gemini, broker authorization, Rego evaluation, a single-use grant, redemption and a bounded result. The current public page is scripted with simulated identities. The new Gemini adapter is prepared and offline-tested, but it does not yet authenticate a real customer or run on the deployed page. It is not the finished full-flow demonstration.

## Small next increment

Reuse the existing `UserOAuth`, `HumanRegistry`, `HumanSession`, Broker and OPAPolicy. Do not build another login system or use a shared invitation password as customer identity. The existing A/B Salesforce subject allowlist can bound the private pilot after genuine OAuth verification. Each person logs in with their own approved Salesforce user; visitors must not share the test users' passwords.

1. Parameterize `UserOAuth` with an exact approved HTTPS Render callback, retaining its current loopback callback by default. Hosted callback validation must check the configured Host and server-owned pending state/PKCE transaction; the present local peer-IP requirement cannot be used as hosted authentication.
2. Add bounded pending OAuth transactions per opaque browser flow. Bind state and S256 verifier server-side to a dedicated Secure, HttpOnly, SameSite=Lax flow cookie so Salesforce's top-level callback can complete. Rotate to a new Secure, HttpOnly, SameSite=Strict application session after authentication. Never return a Salesforce token to the page or model. Clear pending entries on use, cancellation or timeout.
3. Reuse the authenticated token exchange signature, exact org/domain validation and fixed Salesforce Identity Service request. Only `HumanRegistry` assignments for the expected org and approved A/B user IDs are admitted. Store the verified `HumanSession` and its bounded expiry server-side, associated with an opaque browser session. A supplied name, dropdown, email, task or model output cannot authenticate anyone.
4. Bind Gemini to that session's authoritative assignment. The page may request A or B, but cannot choose the authenticated customer, agent mapping or task scope. Replace the synthetic A/B-context construction in `GeminiAgent` with a trusted session/context provider. This provider rechecks session validity and assignment at both grant issuance and redemption. The host-owned agent is acting for that authenticated human; this is not independent production workload authentication.
5. Initially use synthetic downstream data after real customer authentication. Set `human_session_required` true and label execution as a synthetic fixture. Do not falsely set a real Salesforce runtime executor as validated. OPA's existing human-context branch can verify the server-owned org/user mapping while runtime execution is synthetic. Its authoritative lab data must be supplied privately at deployment rather than publishing real identifiers in the repository.
6. Render the actual authentication, agent and broker events. A successful verified login creates the authentication event; it is never fabricated from scenario selection. Show the safe model proposal, host request-binding check, OPA decisions/reasons and observed policy source digest, grant issuance, redemption, downstream count and broker result. Grants, tokens, credentials, raw OAuth state and real user identifiers must not be displayed or logged. Keep model text explicitly untrusted and separate from result evidence.

The Gemini REST client already targets Google's endpoint from any server; it is not tied to Mac Ollama. Its current loopback restriction is a temporary activation gate while hosted authentication/configuration is missing. The next Render configuration must remain disabled by default and reject incomplete auth/key configuration before any model request. The public scripted `/` can remain available while a protected authenticated pilot page and API require the verified customer session on every request. Anonymous visitors, expired sessions, unknown org/users and direct API calls must fail closed before Gemini is invoked.

## Exact approval and user-managed setup needed

- Approve adding `https://ai-access-broker-demo.onrender.com/oauth/callback` to the existing Salesforce Human Login app's allowed callbacks. This has not been added or tested. Review the app's existing OAuth settings and required `api`/`id` scopes; no new write permission is required for the synthetic downstream pilot.
- Enter that app's client key and client secret privately into Render's managed secret environment after hosted auth source review. Do not provide them in chat. No credential is created or accessed by this preparation. The server keeps them and resulting human access tokens in memory.
- Supply the authoritative lab host/org/user-to-A/B mapping privately to the hosted service. Do not copy `.local` or real identifiers into the image/repository. Decide how the OPA data configuration is loaded without publishing it. No Salesforce credentials belong to the Gemini model or MCP adapter.
- Select/create a Gemini API key yourself and enter it privately into Render only after approval. Confirm model access, quota, terms and any cost exposure for the actual project. No billing activation or free allowance is assumed.
- Authorize the first live Salesforce OAuth/Identity Service and Gemini requests. Offline mocks do not verify real account configuration. Restrict the first pilot to the two users with their own approved login credentials and a reviewed Canadian test audience. This is an access restriction, not proof of visitor geography or a universal free-service compliance claim.
- If real Salesforce records are added later, separately approve runtime client credentials and live reads. The existing runtime adapter validates org/user and executes allowlisted projections. A runtime key is not needed to demonstrate the full authentication/authorization flow with synthetic downstream records. Real model-to-Salesforce validation remains deferred.

An open public Gemini client still needs a separate audience/eligibility/cost decision. Google's terms restrict API clients offered to EEA, Swiss or UK users to Paid Services. Neither an A/B selector nor a self-reported country is an adequate substitute for that decision. A private pilot with a verified allowlist is the immediate bounded step; an alternative public demonstration login needs its own genuine provider and enrollment design, not shared passwords.

## Current evidence

The Gemini candidate uses mocked HTTPS responses with actual Broker/OPA. It includes safe event traces and observed Rego source hashes for policy evaluations. This proves the implementation paths under offline inputs, not customer OAuth, live Gemini or hosted Gemini activation. The existing public scripted Render demo was previously verified separately. No Salesforce app edit, callback registration, new secret, API request, billing change, Gemini activation occurred for this candidate. Source publication and disabled deployment were approved separately.
