A request is not permission.

Every agent request should be tied to the user who started it. The broker validates the session token, checks that user’s permitted scope against policy, and issues short-lived permission for the specific action. The agent cannot widen access by claiming another identity or scope.

A/B are temporary demo identities. Records are synthetic. No real-person authentication or enterprise-system connection is used.

What each step does

  1. 1. IdentityA temporary session binds Customer A or B to its permitted records.
  2. 2. Agent requestGemini proposes a specific read for the task.
  3. 3. BrokerValidates the session token and the exact requested action.
  4. 4. PolicyOPA evaluates the Rego policy to decide whether the requested action is permitted. Policies can cover reads and writes; this demo exercises read access.
  5. 5. DataA timed, single-use grant is checked again before a read.

What this demo proves and its limits

The customer’s access does not automatically become the agent’s permission. Each action is scoped, timed and checked against policy. This demonstrates a Zero Trust principle: independently verify the requested access.

The broker uses trusted session identity instead of agent or MCP identity claims. This hosted demo uses temporary sessions and manual Gemini tools; real-person sign-in and MCP belong to the wider architecture/local flow. The model proposes requests; the broker enforces access. Only broker-returned data and read counts are evidence. Model text remains untrusted. A/B scope checks have passed live Gemini testing; prompt override behavior is an advanced test, not a claimed live validation.

Temporary identities do not prove a real human’s identity. This is a lab, with synthetic data and bounded usage. Sessions and quotas are held in memory. A sleeping free service can take about one minute to wake.

Extending this approach

OPA policies can be extended to align with the organisation’s risk appetite, including read and write actions.

Broker audit events can record the actor/session, action, allowed or denied decision, and outcome for each mediated request. This gives visibility into actions routed through the broker.

Risky actions can require approval: Rego returns an approval-required decision, and the broker’s workflow obtains and verifies human approval before execution.

Routine, low-risk actions stay automatic. Meaningful risk or exception thresholds trigger approval for an exact action, scope and time window, helping avoid approval fatigue.

This read-only demo does not implement writes, approval workflows or durable enterprise audit logging.
