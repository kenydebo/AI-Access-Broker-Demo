What this demo proves and its limits

The customer’s access does not automatically become the agent’s permission. Each action is scoped, timed and checked against policy. This demonstrates a Zero Trust principle: independently verify the requested access.

The broker uses trusted session identity instead of agent or MCP identity claims. This hosted demo uses temporary sessions and manual Gemini tools; real-person sign-in and MCP belong to the wider architecture/local flow. The model proposes requests; the broker enforces access. Only broker-returned data and read counts are evidence. Model text remains untrusted. A/B scope checks have passed live Gemini testing. The cross-customer test automatically requests the other record without changing trusted identity. A model that returns no tool call does not exercise broker denial.

Temporary identities do not prove a real human’s identity. This is a lab, with synthetic data and bounded usage. Sessions and quotas are held in memory. A sleeping free service can take about one minute to wake.

Possible extensions, not implemented in this demo

This demo is read-only. Writes, approval workflows and durable enterprise audit logging are not implemented.

OPA policies could be extended to align with the organisation’s risk appetite, including read and write actions.

Durable broker audit events could record the actor/session, action, allowed or denied decision, and outcome for each mediated request. This could give visibility into actions routed through the broker.

Risky actions could require approval: Rego could return an approval-required decision, and a broker workflow could obtain and verify human approval before execution.

Routine, low-risk actions could stay automatic. Meaningful risk or exception thresholds could trigger approval for an exact action, scope and time window, helping avoid approval fatigue.
